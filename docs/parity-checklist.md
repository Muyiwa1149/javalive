**Four real bugs found this way, all fixed and verified live:**

1. **FAQ page was wrongly built as DB-driven months ago.** The screenshot diff against source showed source has 5 category tabs (About Us/Cryptocurrencies/My Account/Investment/NFP) and ~14 real Q&As, while the new app showed one generic question. Checked source's `home/faq.blade.php`: the entire thing is hardcoded (the `faqs` table's one real row, "How can i withdraw", is never actually rendered anywhere) — same "fully static" category as Terms/Privacy's hardcoded text, just never previously checked against the live page. Rebuilt `Faq.vue` verbatim from the Blade source, tabs and all — visually confirmed matching now.
2. **`GlobalExceptionHandler` converted legitimate 404s into 500s.** The crawl caught `/storage/avatar1.jpg` (a copy-trading expert's seed-data photo that was never actually uploaded) returning 500 instead of 404. Root cause: the catch-all `@ExceptionHandler(Exception.class)` was swallowing Spring's own `NoResourceFoundException` before it could produce its normal 404. This affected *any* missing file under `/storage/**` anywhere in the app, not just avatars. Added a dedicated handler.
3. **A real, application-wide UTF-8 encoding bug** — the most significant finding. A 🎉 emoji in the App Settings "welcome message" field rendered as garbled text (`ðŸŽ‰`) in the admin UI. Traced through every layer (raw JDBC, `PreparedStatement`, `getCharacterStream`, `getNString`, a standalone HikariCP pool — all read the value correctly) down to Hibernate itself reading it correctly, proving the corruption happened purely in Spring's HTTP response writing: the JSON response's `Content-Type` never declared a charset, and on this Windows JVM that meant the response bytes were written using the platform's native encoding (Windows-1252) instead of UTF-8, corrupting any non-ASCII character in *any* API response. Fixed globally with `spring.servlet.encoding.{charset: UTF-8, enabled: true, force: true}` in `application.yml` — verified the emoji renders correctly end-to-end in the actual browser afterward. This would have affected any accented name, non-English content, or emoji anywhere in the live app.
4. **One real pre-existing data corruption row**, a side effect of finding bug #3: the *same* emoji was already double-encoded in `javalive_db` itself (confirmed via `keystone`'s raw bytes being correct, so this was introduced during the original Phase 1 migration, not present in source). Scanned every text/varchar column in the entire database for this corruption pattern — found and repaired exactly this one row (`app_settings.welcome_message`); a full re-scan afterward confirmed zero remaining corrupted values anywhere.

Also fixed as part of this pass: carried the `useUnicode=true&characterEncoding=UTF-8` JDBC parameters and the servlet-encoding fix into `application-prod.yml`/`docker-compose.yml`/`.env.example` so production deployments get the same correctness.
